# Zotero 9 端 arXiv 个性化论文推荐插件设计

## 文档状态

- 日期：2026-08-26
- 状态：设计已逐节确认，等待书面规格复核
- 目标运行环境：Zotero 9.0 及以上
- 首要集成基线：macOS 上的 Zotero 9.0.6
- 交付形态：Zotero 桌面插件 `.xpi`

## 1. 背景与结论

当前项目是 Python 程序，通过 GitHub Actions 定时读取 Zotero Web API、抓取 arXiv、生成推荐并发送邮件。现有实现已经具备近期/长期画像、主题聚类和推荐解释的雏形，但存在以下限制：

1. GitHub Actions 每次运行要准备 Python、PyTorch、Embedding 和 LLM 依赖，冷启动慢。
2. 用户必须配置仓库变量、Secrets、邮件和 Workflow，使用门槛较高。
3. 推荐结果停留在邮件里，保存、归类和反馈不能形成可靠闭环。
4. 每次远端任务都要重新获取或计算大量数据，缺少面向单个 Zotero 库的持久增量状态。
5. 用户不能在 Zotero 内直接检查、编辑和回滚画像。

本设计采用纯 TypeScript Zotero 插件。用户在 Zotero 内手动触发推荐，插件直接读取本地文献库、调用用户配置的 OpenAI 兼容 Embedding 服务和可选 LLM 服务、检索 arXiv，并在同一界面完成解释、反馈、下载、查重和归类。

运行推荐不依赖 Python、GitHub Actions、SMTP 或独立后端。现有 Python/Action 实现暂时保留为旧版回退路径；插件稳定后再单独决定是否弃用。

## 2. 产品目标

核心工作流如下：

1. 用户打开 Zotero 的“今日推荐”页签。
2. 用户选择全部或指定兴趣画像、推荐数量和日期范围。
3. 插件根据本地 Zotero 论文和历史反馈生成近期、长期兴趣画像。
4. 插件检索近期 arXiv 论文，按相关度和多样性给出 Top N 推荐。
5. 每篇论文展示可复盘的推荐依据和各分项得分。
6. 用户选择“保存并归类”“稍后”或“不感兴趣”。
7. 保存时完成重复检测、Zotero 元数据入库、收藏夹选择和 PDF 附件下载。
8. 明确反馈持续修正画像权重和排序权重。

成功标准不是“邮件能够发出”，而是：用户可以在 Zotero 内低成本完成发现、判断、保存、归类和反馈，并能解释任一推荐为什么出现。

## 3. 调研结论

### 3.1 类似方案的启发

| 项目或产品 | 可借鉴能力 | 不直接采用的原因 |
| --- | --- | --- |
| PaperFlow | 本地状态、短期/长期兴趣漂移、反馈事件和可测试的推荐流水线 | 没有 Zotero 原生入库与归类闭环，不能替代插件体验 |
| Semantic Scholar Research Feed | 保存是正反馈，“不相关”是显式负反馈 | 不能使用用户完整 Zotero 结构和本地收藏夹语义 |
| arxiv-sanity-preserver | 书签反馈驱动轻量判别器，证明少量反馈能改善排序 | 界面和数据模型不围绕 Zotero 工作流 |
| ResearchRabbit / Litmaps | Zotero 联动、文献发现和收藏同步具有明确用户需求 | 主要基于引文图，画像可编辑性和逐项解释不满足本项目目标 |
| Neozot 等早期项目 | 证明 Zotero 与论文发现联动可行 | 项目成熟度、维护状态和闭环能力不足 |

### 3.2 技术路线判断

考虑过三条路线：

1. 继续使用 GitHub Actions，并增加反馈页面。
2. Zotero 插件加本地或远端 Python 服务。
3. Zotero 纯 TypeScript 插件，模型使用用户可配置 API。

选择第三条。它最符合“用户自己操作、不开 Zotero 就不运行、不配置 Actions、单设备使用”的约束。代价是需要在 JavaScript/TypeScript 环境实现画像和排序逻辑，并且 Zotero 9 的插件生态需要先完成兼容性验证。

## 4. MVP 范围

### 4.1 包含

- Zotero 9 桌面端插件，覆盖 macOS、Windows 和 Linux。
- 当前个人 Zotero 库；默认使用全库，可排除指定收藏夹。
- 用户手动触发，不提供后台定时任务。
- arXiv 数据源，默认领域为 `cs.CV` 和 `cs.CL`，可在设置中修改。
- 用户可配置 OpenAI 兼容 Embedding API。
- 可选 OpenAI 兼容 LLM API，用于最终 Top N 的中文摘要。
- 近期兴趣、长期兴趣、多主题画像、人工画像覆盖和版本回滚。
- 推荐数量 1 到 30，默认 5。
- 全部、单个或多个兴趣画像定向推荐。
- 可解释排序、查重入库、PDF 附件、收藏夹建议和反馈闭环。
- 本地诊断、导出和故障恢复。

### 4.2 不包含

- Zotero 未启动时的后台执行。
- GitHub Actions、SMTP 邮件和用户自建服务端。
- 多设备画像或反馈同步。
- Zotero 群组库写入。
- 移动端。
- PDF 全文、笔记或批注上传给模型。
- PDF 全文深度总结。
- arXiv 以外的论文源。
- 团队画像、多人协作或集中账号管理。

这些能力可以在首版闭环稳定后独立设计，不进入 MVP 依赖链。

## 5. 兼容与工程策略

### 5.1 仓库布局

现有 Python 文件继续保留在仓库根目录。新实现放在独立目录，减少对已运行邮件链路的影响：

```text
zotero-plugin/
  addon/                 # manifest、locale、图标和静态 UI
  src/
    bootstrap/           # 插件生命周期与注册
    ui/                  # 今日推荐、画像编辑、设置、诊断
    domain/
      profiles/          # 画像生成、合并、拆分和版本
      ranking/           # 特征、打分、多样性重排
      feedback/          # 事件与在线权重
      importing/         # 查重、归类和任务状态机
    infrastructure/
      zotero/            # Zotero 读取、写入、通知和附件适配
      arxiv/              # 候选检索与元数据规范化
      models/             # Embedding 与可选 LLM 客户端
      storage/            # 插件数据库、迁移、备份和缓存
    shared/               # 类型、错误、日志、取消和工具函数
  test/
    unit/
    integration/
    fixtures/
```

运行时为纯插件。Node.js 和包管理器只用于开发、测试、构建和生成 XPI。

## 6. 系统架构

```text
Zotero 9 UI
  │
  ├── RecommendationController ── RunCoordinator ── OperationTaskRepository
  │                                  │
  │                                  ├── CorpusReader
  │                                  ├── ProfileEngine
  │                                  ├── ArxivClient
  │                                  ├── EmbeddingClient
  │                                  ├── Ranker
  │                                  └── OptionalSummaryClient
  │
  ├── TaskCenter ──────────────── Progress / Continue / Retry / Cancel
  ├── SetupWizard ─────────────── ModelConnectionTester / CorpusEstimator
  ├── ProfileEditor ───────────── ProfileRepository
  ├── ImportController ────────── DuplicateDetector / ZoteroWriter / PdfAttacher
  ├── FeedbackController ──────── FeedbackRepository / WeightLearner
  └── DiagnosticsView ─────────── RunLog / CacheStats / SanitizedExporter

All components ────────────────── Plugin-owned local SQLite database
Zotero adapters ───────────────── Supported Zotero APIs, never direct zotero.sqlite writes
```

### 6.1 边界原则

- `domain` 不依赖 Zotero UI，可以用固定数据做单元测试。
- Zotero API、网络、数据库和时钟都通过接口注入。
- Zotero 启动时只注册界面、首选项和变更监听器，不自动访问 Zotero 语料、arXiv 或模型服务。
- 重启后将未完成任务统一标记为 `interrupted` 并显示“继续”；只有用户点击后才恢复网络或计算阶段。
- 排序不依赖 LLM，LLM 失败不能改变推荐顺序。
- 系统画像与用户覆盖分开存储，系统重建不能覆盖用户意图。
- 长任务通过 `RunCoordinator` 提供进度、取消、继续和互斥控制。
- 推荐、画像、摘要、入库和附件任务使用同一状态协议与任务中心，但保持各自独立的幂等检查点。
- 新画像或新排序权重只在完整成功后原子发布，不暴露半成品状态。

## 7. 用户界面

### 7.1 “今日推荐”独立页签

顶部工具栏包含：

- 画像选择：全部兴趣、一个画像或多个画像。
- 推荐数量：1 到 30，默认 5。
- 时间范围：自上次成功检索起，用户也可选择 1、3、7 或 14 天。
- arXiv 分类：默认 `cs.CV`、`cs.CL`。
- “刷新推荐”命令和当前阶段进度。
- 画像、设置、历史和诊断入口。

推荐卡片展示：

- 标题、作者、arXiv 分类、提交日期和链接。
- LLM 关闭时的 arXiv 原文摘要。
- LLM 开启时的处理后中文摘要，并保留“查看原文摘要”。
- 0 到 100 的本次候选池相对相关度。
- 命中的近期/长期画像、代表 Zotero 论文和关键词。
- 六项原始分数、负反馈扣分和多样性调整。
- 使用的画像版本、Embedding 模型指纹和推荐运行时间。
- “保存并归类”“稍后”“不感兴趣”三个主要操作。

### 7.2 画像编辑器

用户可以：

- 修改显示名称和关键词。
- 调整画像权重。
- 添加或移除代表论文。
- 指定必须包含或排除的论文。
- 置顶、停用或锁定画像。
- 新建人工画像。
- 合并画像。
- 查看拆分预览后确认拆分。
- 查看版本差异、恢复系统建议或回滚历史版本。

每个画像展示成员数、平均组内相似度、与上一版成员重合率、主要收藏夹占比和代表论文。界面不再把通用相似度包装成不可靠的“置信度”。

Zotero 条目右键菜单为符合语料条件的选中论文提供“加入兴趣画像”和“从兴趣画像排除”。操作只写用户覆盖；缺少向量的论文标记为待处理，由下一次用户手动运行时计算，不在右键操作后隐式访问模型。

### 7.3 任务中心

任务中心位于“今日推荐”页签内，使用紧凑列表显示推荐、画像、摘要、入库和 PDF 附件任务：

- 当前阶段、已完成量/总量、阶段耗时、缓存命中和最近用户可读事件。
- `queued`、`running`、`interrupted`、`failed`、`completed`、`cancelled` 状态及明确的下一步。
- 运行中任务可取消；失败任务可重试；中断任务由用户点击继续；完成任务可查看结果或清理运行细节。
- 支持按进行中、失败和完成筛选，但 MVP 不提供任务优先级、自动扫描或后台调度。
- 错误详情只显示稳定错误码和脱敏信息，完整诊断通过诊断页导出。

关闭或重启 Zotero 不会丢失已提交检查点。插件重新启动后不得自动续跑；所有遗留 `running` 状态先转换为 `interrupted`。

### 7.4 首次使用

首次进入“今日推荐”时显示设置向导：

1. 配置并测试必需的 Embedding 服务；成功结果显示模型名、向量维数和请求耗时。
2. 选择需要排除的收藏夹。
3. 展示有效论文数、将发送的字段、预计批次和 Token。
4. 用户明确点击后才开始首次画像构建。
5. LLM 保持关闭，用户可以跳过其配置；启用前单独测试连接。

连接失败时向导显示脱敏后的 Base URL、HTTP 状态或稳定错误码以及可执行的排查建议，不显示 API Key、Authorization、标题或摘要。用户可以离开向导浏览历史结果，但 Embedding 测试通过前不能启动新的画像或推荐任务。

如果没有有效 Zotero 论文且也没有人工画像，界面不生成伪画像，而是提示补充带摘要的论文或新建人工画像。人工画像至少需要名称以及关键词或代表论文之一。

## 8. 本地数据模型

插件使用独立 SQLite 文件，存放于 Zotero 数据目录下的插件专属位置。严禁直接写 `zotero.sqlite`。

| 表 | 主要内容 |
| --- | --- |
| `schema_meta` | 数据库版本、创建时间和最近迁移状态 |
| `item_snapshots` | library ID、item key、Zotero item version、标题摘要哈希、dateAdded、收藏夹指纹 |
| `embedding_generations` | 规范化 Base URL 哈希、模型名、向量维数、归一化版本和世代状态 |
| `embedding_cache` | 对象类型、对象 ID、内容哈希、模型世代、向量和创建时间 |
| `profile_versions` | 语料指纹、算法配置、模型世代、创建原因、草稿/已发布状态 |
| `profiles` | 画像 lineage ID、类型、系统名、质心、统计指标和优先级 |
| `profile_members` | 画像版本、item key、相似度和代表论文顺序 |
| `profile_overlays` | 用户名称、关键词、权重、锁定、停用、包含/排除和人工结构操作 |
| `recommendation_runs` | 查询范围、目标画像、候选数、阶段耗时、模型和画像版本 |
| `recommendation_candidates` | arXiv 元数据、各分项得分、最终分数、排序和展示状态 |
| `summary_cache` | arXiv ID、LLM 模型、Prompt 版本、语言和中文摘要 |
| `feedback_events` | 不可变事件：保存、稍后、拒绝原因、归类修正和上下文 |
| `ranking_weight_versions` | 默认或学习后权重、训练样本数、更新原因和回滚关系 |
| `operation_tasks` | 任务类型、状态、阶段、完成量、检查点、重试次数、脱敏错误、关联运行和时间戳 |
| `import_tasks` | 查重、元数据、收藏夹、附件、反馈各阶段状态和 Zotero item key |

保留策略：

- 最近 20 个画像版本。
- 推荐运行和候选元数据默认保留 90 天。
- arXiv 候选向量按 14 天和 256 MiB 的双重上限做 LRU 清理，先达到的限制生效。
- 成功入库任务的运行细节保留 30 天。
- 完成或取消的通用任务明细保留 30 天；进行中、失败和中断任务保留到用户处理。
- 反馈事件和人工画像覆盖长期保留，直到用户明确清除。
- 更换 Embedding 模型创建新世代，旧世代可回退但绝不混用。

数据库迁移前自动备份。Embedding、候选缓存和系统画像可从 Zotero 与 arXiv 重建；反馈事件和人工覆盖不可推导，备份优先级最高。

## 9. 语料与画像

### 9.1 语料选择

- 默认读取个人库中的 `journalArticle`、`conferencePaper` 和 `preprint`。
- 条目必须有标题和摘要。
- 默认包含全库，用户可以按收藏夹排除。
- 只读取生成画像所需的字段：item key、item version、标题、摘要、标签、dateAdded 和收藏夹。
- Zotero 通知器仅将变更条目标记为脏数据，真正的 Embedding 调用由用户下一次手动运行触发。

Embedding 缓存键为：

```text
item key + Zotero item version + content hash + model generation
```

没有变化的论文不会重新请求 Embedding。

### 9.2 长期兴趣

- 使用全部有效语料。
- 长期画像表示稳定研究方向，不因短期突发收藏立即消失。
- 手工置顶和画像权重作为独立覆盖层参与排序。

### 9.3 近期兴趣

- 基础窗口为最近 90 天加入 Zotero 的论文。
- 最近 90 天“保存并归类”的推荐论文也进入近期兴趣。
- 按行为时间做指数衰减，默认半衰期 30 天。
- 用户改动系统时间或数据不足时，记录所用窗口和有效样本数。

### 9.4 聚类与画像数量

- 向量先做 L2 归一化。
- 使用确定性种子的轻量 K-Means/mini-batch K-Means；归一化向量上的欧氏距离等价于余弦排序。
- 候选 `K` 在 3 到 12 之间，通过抽样后的组内误差改善量和复杂度惩罚选择，不执行全库两两距离计算。
- 全量分配复杂度为 `O(N × K)`。
- 少于 15 篇有效论文时生成 1 个画像；15 到 29 篇最多生成 2 个；30 篇以上使用 3 到 12 个。
- 单次增量运行只重算变化条目并检查漂移；任一画像质心移动超过 0.15 余弦距离，或成员变化率超过 20%，视为明显漂移并执行完整重聚类。
- 当累计变化条目超过有效语料的 10%，或距离上次完整重建超过 30 天时，也执行完整重聚类。
- 孤立项默认折叠到“其他”，不会用单篇论文制造高置信画像。

### 9.5 稳定身份和命名

新旧同类型画像两两计算 `0.7 × 成员 Jaccard 重合率 + 0.3 × 质心余弦相似度`，按分数从高到低做一对一匹配；分数至少 0.60 才继承上一版 lineage ID，否则创建新 lineage。用户覆盖绑定 lineage ID，而不是一次性的聚类编号。

画像名称和关键词由代表论文、标题短语、标签与领域词典确定性生成。MVP 的 LLM 只处理推荐摘要，不参与画像命名。用户可以修改并锁定名称和关键词。

## 10. arXiv 候选生成

- 默认查询 `cs.CV` 和 `cs.CL`，设置页允许增删分类。
- 默认从上次成功检索时间继续，最长自动回看 7 天，避免 Zotero 数日未打开时永久漏掉论文。
- 初次运行默认回看 3 天。
- 用户可手动选择 1、3、7 或 14 天；14 天只影响当前运行。
- 对 arXiv ID、DOI、规范化 URL、规范化标题和版本做候选去重。
- 已保存、明确拒绝和近期已推荐论文从候选池过滤；“稍后”在 7 天后可重新出现。
- 目标画像影响排序，不用过窄关键词在检索入口提前截断语义候选。
- 候选量超过 1000 时，先用画像关键词对标题摘要做 BM25 词法预筛，保留最高 800 篇和 200 篇按运行日期固定种子的探索样本，再请求 Embedding。
- arXiv 候选向量按 `arXiv ID + version + model generation` 缓存，并遵守第 8 节的 14 天/256 MiB 清理策略。
- 网络客户端遵守 arXiv 限流，批次之间节流，并对 429、5xx 和超时使用带抖动的指数退避。

## 11. 推荐排序

### 11.1 特征

对每篇候选论文计算六个可解释特征，全部归一化到 0 到 1：

| 特征 | 默认权重 | 定义 |
| --- | ---: | --- |
| `recent_similarity` | 0.35 | 与所选近期画像的最大加权余弦相似度 |
| `long_term_similarity` | 0.25 | 与所选长期画像的最大加权余弦相似度 |
| `representative_similarity` | 0.20 | 与命中画像前三篇代表 Zotero 论文的最大相似度 |
| `keyword_match` | 0.10 | 标题摘要对用户关键词和系统关键词的加权覆盖 |
| `manual_priority` | 0.10 | 用户画像权重、置顶和明确包含规则产生的受限增益 |
| `negative_similarity` | -0.25 | 与“主题不相关”负反馈向量的最大时间衰减相似度 |

原始相关度：

```text
raw = 0.35 * recent
    + 0.25 * long_term
    + 0.20 * representative
    + 0.10 * keyword
    + 0.10 * manual
    - 0.25 * negative
```

“全部兴趣”采用候选最匹配画像，不把多个宽泛画像简单平均。选择单个或多个画像时，只在所选画像内计算。

### 11.2 多样性重排

原始相关度之后执行 MMR 风格重排：

- 已选论文与候选越相似，候选多样性分越低。
- 默认使用 `rerank = raw - 0.12 × 与已选论文的最大余弦相似度`，并把调整值单独记录。
- 当 `N >= 5` 时，单一主画像原则上不超过结果的 60%。
- 如果其他画像的最佳候选原始分低于当前不受限候选的 85%，允许突破配额，不用低质量论文凑多样性。
- 多样性调整单独记录，用户可以看到论文是因相关度还是覆盖其他兴趣而上升。

### 11.3 展示分数

0 到 100 分表示论文在本次候选池中的相对相关度，不是命中概率。对多样性重排后的排序分使用候选池 5% 到 95% 分位裁剪后线性映射，并记录原始相关度、重排调整和候选池规模，避免跨天误比较。

## 12. 反馈学习

### 12.1 反馈语义

| 操作 | 学习含义 | 其他行为 |
| --- | --- | --- |
| 保存并归类 | 强正反馈 | 进入近期兴趣，记录最终收藏夹 |
| 稍后 | 中性 | 当前运行隐藏，7 天后可再次推荐 |
| 不感兴趣：主题不相关 | 显式语义负反馈 | 进入负反馈向量集合 |
| 不感兴趣：已读过 | 非语义抑制 | 只屏蔽该论文 |
| 不感兴趣：重复 | 非语义抑制 | 合并或关联已有条目，不训练负向主题 |
| 无操作 | 无信号 | 不参与训练 |

每个反馈事件带稳定幂等键。同一推荐运行中对同一论文重复点击不会生成多个训练样本。

### 12.2 可解释在线权重

- 冷启动始终使用默认权重。
- 至少积累 20 个显式事件，并且正样本和“主题不相关”负样本各不少于 5 个，才允许学习。
- 使用六个已展示特征训练带 L2 正则的轻量逻辑回归，不训练不可解释的端到端模型。
- 正向五项权重保持非负，负反馈权重保持非正。
- 每次发布相对上一版最多变化 0.03；正向权重长期限制在各自默认值上下 0.10 并重新归一化为总和 1，负反馈权重限制在 `-0.40` 到 `-0.10`。
- 每新增 10 个有效事件最多生成一个候选权重版本。
- 新权重先做历史回放；指标恶化则不发布。
- 权重版本记录样本数、变化原因和指标，用户可查看、禁用、重置或回滚。
- 用户锁定的画像权重不被在线学习覆盖。

## 13. LLM 摘要

- LLM 默认关闭。
- 关闭时直接显示 arXiv 原文摘要，不发起任何 Chat Completions 请求。
- 开启后只处理最终展示的 Top N，不处理完整候选池和 Zotero 语料库。
- 输入仅包含标题和 arXiv 摘要。
- 输出为中文摘要，固定包含“研究问题、主要方法、摘要中报告的结果”三个部分。
- Prompt 明确要求不补充摘要之外的结论；界面标记“AI 中文摘要”。
- 原文摘要始终可查看。
- LLM 失败、超时或返回空内容时自动退回原文摘要，不影响排序、反馈或保存。
- 缓存键为 `arXiv ID + version + LLM model + prompt version + language`。
- LLM 不参与画像、关键词、归类、评分和推荐解释。

## 14. 模型配置

Embedding 和 LLM 分别配置，均兼容常见 OpenAI 风格接口。

Embedding 设置：

- Base URL
- API Key
- 模型名
- 批大小
- 超时和最大重试次数
- “测试连接”

Embedding 是语义画像和推荐的必需配置。连接未通过时，插件允许浏览设置和历史结果，但不启动新的画像或推荐运行。用户可以把 Base URL 指向明确允许的本机 OpenAI 兼容服务。

LLM 设置：

- 启用开关，默认关闭
- Base URL
- API Key
- 模型名
- 超时和最大重试次数
- “测试连接”

MVP 使用 `/embeddings` 和 `/chat/completions` 语义，不支持供应商私有批处理协议，也不建立面向特定厂商的 Provider Registry。Embedding 和 LLM 只是两个独立角色，均可配置云端或本机 OpenAI 兼容地址。

连接测试使用不含用户论文内容的固定最小样例。Embedding 测试验证鉴权、响应结构、向量维数、有限数值和耗时；LLM 测试验证鉴权、非空文本响应和耗时。测试结果只持久化成功时间、模型指纹和维数，不持久化测试响应正文。

首次全库向量化前展示有效论文数、预计批次数和输入 Token 估算。只有用户配置单价后才估算费用，界面不内置可能过期的价格。

模型指纹至少包括规范化 Base URL 哈希、模型名、向量维数和归一化版本。切换服务地址、模型或维数时创建全新 Embedding 世代。

## 15. 入库、归类与 PDF

### 15.1 重复检测

保存前和真正写入前各执行一次，优先级如下：

1. arXiv ID 精确匹配。
2. DOI 规范化后精确匹配。
3. arXiv URL 规范化后匹配。
4. 标题规范化加年份匹配。

如果已存在父条目：

- 不创建新条目。
- 保留已有收藏夹，只补充用户本次选择的收藏夹。
- 缺少 PDF 时可补附件。
- 仍记录一次正反馈，并关联已有 item key。

### 15.2 新条目

- 使用推荐候选中已经校验的 arXiv 元数据直接创建 Zotero `preprint`，填写标题、作者、摘要、日期、DOI、URL、repository、archive 和 arXiv ID。
- 不把网页 Translator 作为主路径，避免翻译器版本变化、重复下载附件和不可控字段覆盖。只有未来遇到候选元数据无法表达的明确字段时，才单独设计可选补充流程。
- 元数据父条目先提交成功，再进入附件阶段。

### 15.3 收藏夹建议

- 根据命中画像成员的收藏夹分布、代表论文收藏夹和用户历史修正生成建议。
- 对命中画像中最相似的 20 篇成员做收藏夹加权投票，代表论文权重乘 2，最近的用户分类修正按 180 天半衰期加入投票。
- 显示建议收藏夹和依据，用户保存前可以修改。
- 只有第一名票数占比至少 55%，且领先第二名至少 15 个百分点时才自动建议该收藏夹；否则选择插件维护的“待分类”收藏夹。
- 若“待分类”不存在，首次需要时创建一次。
- 用户修正会成为后续分类信号，但不会自动移动已存在的其他论文。

### 15.4 PDF 附件

- PDF 是元数据父条目的独立子任务。
- 下载前验证 HTTPS URL；下载后验证 HTTP 状态、Content-Type、PDF 文件头和大小。默认上限为 100 MiB，可在 20 到 500 MiB 之间配置。
- 通过 Zotero 附件 API 保存为存储型子附件。
- 支持进度、取消和仅重试附件。
- 附件失败时父条目、收藏夹和正反馈继续保留，任务显示“附件待重试”。

### 15.5 幂等任务

`import_tasks` 为每次用户意图生成稳定任务 ID。核心入库状态与附件状态独立：

```text
core:       pending -> duplicate_checked -> metadata_saved
                   -> classified -> feedback_recorded -> completed

attachment: not_requested | pending -> saved | failed | cancelled
```

核心流程完成且附件失败时，任务整体显示 `completed_with_attachment_error`。正反馈不会因为附件失败丢失，也不会因重复保存被重复计数。任一阶段重试都从最后一个已提交检查点继续，反复点击不会重复创建父条目。

`operation_tasks` 是任务中心的通用投影，`import_tasks` 保留入库领域的细粒度事实。两者通过稳定任务 ID 关联，前者不得替代后者的幂等状态机。

## 16. 错误处理与恢复

| 故障 | 用户结果 | 恢复行为 |
| --- | --- | --- |
| arXiv 检索失败 | 保留最近一次成功结果并标注时间 | 重试当前检索，不清空缓存 |
| Embedding 批次失败 | 已发布画像继续可用 | 不发布半成品画像，从失败批次继续 |
| 新候选 Embedding 不完整 | 不静默生成不完整语义排名 | 保留上次推荐，提示重试 |
| LLM 摘要失败 | 展示 arXiv 原文摘要 | 只重试摘要 |
| Zotero 元数据写入失败 | 不进入附件和反馈阶段 | 修复后重试写入 |
| PDF 失败 | 父条目和归类保留 | 只重试附件 |
| 数据库迁移失败 | 使用迁移前备份，插件进入只读诊断状态 | 恢复备份或重建可推导数据 |
| 用户取消 | 已提交阶段保留 | 下次从检查点继续或新建运行 |
| Zotero 在任务中关闭 | 保留最后已提交检查点 | 下次启动标记中断，等待用户点击继续 |

同一时间只允许一个推荐或画像重建任务运行；入库任务可以排队。所有长操作都不能阻塞 Zotero 主界面。

## 17. 隐私与安全

- API Key 只保存在本机 Zotero 偏好设置，不同步到 Zotero 云端。
- 设置页使用密码输入框；Key 不写日志、不进入导出、不展示完整值。
- MVP 不宣称 Key 在本地加密；拥有本机账户或文件系统权限的人可能读取它。
- 远端 Base URL 必须是 HTTPS；`localhost` 和回环地址可由用户明确允许 HTTP。
- 首次全库 Embedding 前必须展示将发送的字段和数量并要求确认。
- Embedding 只发送标题和摘要。
- LLM 只发送最终 Top N 的标题和摘要，且默认关闭。
- 笔记、批注、PDF 全文、附件路径、收藏夹名称和用户身份不发送给模型。
- 诊断导出只包含状态码、错误分类、阶段耗时、批次数、模型指纹、缓存统计、画像版本和脱敏配置。
- 诊断包默认不含标题摘要；用户主动勾选样例数据时再次提示隐私风险。

## 18. 可观测性与解释

每次运行记录：

- 运行 ID、开始结束时间和各阶段耗时。
- arXiv 查询、日期范围、候选数、过滤数和最终数量。
- 目标画像及版本。
- Zotero 有效语料数、变化数和排除数。
- Embedding/LLM 模型指纹、请求批次、缓存命中和重试。
- 每篇候选的六项特征、原始得分、多样性调整、相对分和排名。
- 命中画像、代表论文和关键词。
- 用户动作、拒绝原因、收藏夹建议与最终选择。
- 任务状态迁移、检查点、取消/继续/重试来源和最终结果。

推荐解释由这些确定性事实生成，不要求 LLM 解释自己的排序。日志分为用户可读事件和调试详情，生产模式不输出密钥或论文内容。

## 20. 推荐效果评估

### 20.1 离线时间回放

1. 选择历史时间截点 `T`。
2. 只使用 `T` 之前已加入 Zotero 的论文生成画像。
3. 从 `T` 之后对应日期的 `cs.CV`、`cs.CL` arXiv 论文构建候选池。
4. 将用户后来真实收藏且可匹配 arXiv 的论文作为正例。
5. 同时比较弱基线“全库单质心余弦排序”和当前提交 `7d54812` 的近期/长期多画像算法，再与本设计排序比较。当前算法以冻结的 TypeScript 等价实现运行，并用固定夹具验证与 Python 输出的排序一致性。
6. 滚动至少 5 个时间截点，禁止将未来收藏或反馈泄漏到过去。

指标：

- Recall@5、Recall@10
- MRR
- nDCG@5、nDCG@10
- 画像覆盖率
- 列表内平均相似度
- 单画像结果占比

如果有至少 20 个可匹配历史正例，验收门槛为：`nDCG@5` 或 `Recall@10` 相对两个基线中表现更强者提升至少 10%，另一项不得下降超过 2%。如果样本不足，不宣称算法提升；工程验收通过后只发布 Beta，并继续收集在线数据。

### 20.2 在线观察

- 保存率。
- “主题不相关”拒绝率。
- “已读/重复”抑制率。
- 收藏夹建议修正率。
- 稍后转保存率。
- 各阶段耗时、失败率、缓存命中、批次和 Token。

提交 `7d54812` 的当前算法保留为影子排名，只记录同一候选池中的排名差异，不向用户额外展示一套结果。无操作始终不算负反馈。

至少积累 30 个显式在线事件后再评估自适应权重；达到第 12.2 节样本门槛前不启用学习。

## 21. MVP 验收标准

必须全部满足：

1. Zotero 9.0.6 可以安装、启用、禁用和卸载插件，关闭 Zotero 后不运行任务。
2. 不需要 Python、GitHub Actions、SMTP 或独立后端即可完成完整工作流。
3. 推荐数量和目标画像可以控制，用户可以编辑、锁定和回滚画像。
4. 无库变更时不重复请求 Zotero 论文 Embedding。
5. 切换 Embedding 模型不会混用旧向量。
6. 每篇推荐可以追溯到画像、代表论文、关键词、各分项得分、模型和版本。
7. LLM 默认关闭；关闭时是原文摘要，开启后是中文摘要并可查看原文。
8. 同一论文连续保存 10 次只产生一个 Zotero 父条目。
9. PDF 下载失败不删除父条目，重试不重复入库。
10. LLM、Embedding、arXiv 和 PDF 任一故障不会损坏已发布画像、反馈或已保存条目。
11. API Key 不出现在日志、错误提示或诊断导出。
12. 数据库迁移失败可以恢复，反馈和人工覆盖有备份。
13. 满足第 20 节适用的离线质量门槛；样本不足时只能作为 Beta 发布并明确标注证据不足。
14. 已有缓存时，点击推荐页后 1 秒内显示可交互界面；网络任务继续异步更新状态。
15. 在当前 Mac 上，对 1000 个已有向量的候选和最多 12 个画像完成本地打分与重排不超过 2 秒；网络和 LLM 时间单独计量。
16. 任务中心可以展示、取消、重试和继续任务；重启 Zotero 后任何任务都不会自动联网续跑。

## 22. 分阶段实施

### Stage 1：插件底座与 Zotero 9 兼容

交付：

- `zotero-plugin/` 构建、开发加载和 XPI 打包。

- 插件数据库、迁移、备份和日志。
- Embedding/LLM 设置、密钥脱敏和连接测试。
- 任务中心外壳、统一任务状态和“启动后中断、用户继续”语义。

门禁：安装、重载、卸载无残留；数据库迁移测试通过；Zotero UI 不被网络调用阻塞。

### Stage 2：增量索引与画像

交付：

- 全库减排除收藏夹的语料读取。
- 增量 Embedding 和模型世代。
- 近期/长期画像、稳定 lineage、质量指标。
- 画像编辑、锁定、合并、拆分预览、版本与回滚。

门禁：无变更二次运行 Embedding 请求数为 0；更换模型生成独立世代；人工覆盖在重建后保留。

### Stage 3：推荐工作台

交付：

- arXiv 检索、缓存、去重和限流。
- 六特征排序、多样性重排和相对得分。
- 推荐数量、画像选择、日期和分类控制。
- 逐项解释和诊断。
- LLM 默认关闭、可选中文摘要和原文回退。

门禁：固定夹具排名可复现；所有分项能从存储记录重算；LLM 故障不改变排序。

### Stage 4：入库、归类与反馈闭环

交付：

- 双重查重、幂等入库状态机。
- 收藏夹建议、用户修改和“待分类”。
- PDF 进度、取消和独立重试。
- 保存、稍后、三类拒绝反馈。
- 受约束在线权重版本和回滚。

门禁：重复保存测试、附件故障注入、反馈语义和权重约束全部通过。

### Stage 5：评估与发布

交付：

- 历史时间回放工具和基线对比报告。
- macOS、Windows、Linux 的 Zotero 9 冒烟结果。
- 故障注入、数据库升级和诊断导出验证。
- 用户安装、模型配置、隐私说明和问题排查文档。
- Beta XPI 和更新清单。

门禁：第 21 节所有适用条目通过，未通过项不得用“后续优化”替代。

## 23. 主要风险与控制

| 风险 | 控制措施 |
| --- | --- |
| Zotero 9 与参考模板存在版本差 | 以本地 Zotero 9 模板为底座，Stage 1 建立 API 兼容矩阵并锁定依赖 |
| 全库初次 Embedding 慢或产生费用 | 运行前估算、分批、进度、取消、检查点和增量缓存 |
| 多主题画像名称漂移 | 稳定 lineage、确定性命名、版本差异和人工锁定 |
| 少量反馈导致过拟合 | 最低样本门槛、L2 正则、权重边界、离线门禁和回滚 |
| 负反馈污染兴趣 | 仅“主题不相关”进入语义负样本；已读和重复只抑制论文 |
| LLM 幻觉影响判断 | LLM 不参与排序；仅摘要增强，保留原文并明确标识 |
| PDF 或元数据重复 | 两次查重、稳定任务 ID、分阶段提交和幂等重试 |
| 自动恢复造成意外费用或联网 | 重启统一转 `interrupted`，必须由用户点击继续 |
| 本地数据库损坏 | 迁移前备份；可推导数据可重建；反馈与人工覆盖优先恢复 |
| 远端模型隐私 | 默认最小字段、LLM 默认关闭、首次确认、HTTPS 和脱敏诊断 |

## 24. 已确定的产品决策

- 运行位置：全部在 Zotero 端，由用户手动触发。
- 模型：Embedding 使用用户配置的 OpenAI 兼容 API；LLM 同类接口但可选。
- LLM 行为：默认关闭显示原文摘要，开启后生成中文摘要。
- 状态：仅本机单设备，不做同步。
- 主入口：独立“今日推荐”页签。
- 任务：统一任务中心；启动后不自动恢复，用户明确点击才继续。
- 画像：全库默认，可排除收藏夹；近期和长期分开；用户可编辑。
- 推荐：数量可调，可选择全部或指定画像。
- 归类：建议现有收藏夹，用户确认；低置信度进入“待分类”。
- 入库：直接用已校验 arXiv 元数据创建 `preprint`，PDF 作为独立可重试子任务。
- 反馈：保存、稍后、不感兴趣；无操作不是负反馈。
- 可解释性：排序特征、画像、代表论文、模型、版本和运行诊断都可查看。
- 支持版本：Zotero 9，首要基线为本机 9.0.6。
